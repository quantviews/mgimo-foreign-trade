# Модель данных для гармонизированных таблиц таможенной статистики

Этот документ описывает стандартизированную модель данных, используемую для итоговых, гармонизированных наборов данных в директории `data_processed`. Все сырые данные, собранные из разных источников (Китай, Турция, Индия и т.д.), преобразуются в соответствие с этой схемой.

## Схема таблицы `unified_trade_data`

| Название колонки | Тип данных    | Описание                                                                                                                                    | Пример         |
|------------------|---------------|---------------------------------------------------------------------------------------------------------------------------------------------|----------------|
| `NAPR`           | `VARCHAR`     | **Направление торгового потока.** Указывает, является ли торговый поток импортом или экспортом по отношению к Российской Федерации. (`ИМ` = Импорт, `ЭК` = Экспорт). | `ИМ`           |
| `PERIOD`         | `DATE`        | **Отчетный период.** Первый день месяца, за который представлены данные. Всегда хранится в формате `YYYY-MM-DD`.                          | `2023-01-01`   |
| `STRANA`         | `VARCHAR`     | **Страна-партнер.** Двухбуквенный ISO-код страны-партнера (например, `CN` для Китая, `TR` для Турции).                                          | `CN`           |
| `TNVED`          | `VARCHAR`     | **Код ТН ВЭД (Товарная номенклатура внешнеэкономической деятельности).** Полный товарный код в строковом виде. Ведущие нули источника сохраняются; в merge-слое короткие коды при необходимости дополняются справа до 10 знаков. | `0101210000`   |
| `EDIZM`          | `VARCHAR`     | **Дополнительная (supplementary) единица измерения.** Единица измерения для колонки `KOL`, как она указана в исходных данных (например, "Number of item", "kg"). `?` означает отсутствующую или неизвестную единицу. | `Number of item` |
| `EDIZM_ISO`      | `VARCHAR`     | **Код стандартизированной единицы измерения.** Код из справочника `metadata/edizm.csv` для унификации единиц измерения. | `166`          |
| `STOIM`          | `DECIMAL`     | **Стоимость (USD).** Статистическая стоимость товаров в **долларах** США (в единицах, не в тысячах).                                              | `12500500`     |
| `NETTO`          | `DECIMAL`     | **Вес нетто (кг).** Вес нетто товаров в килограммах.                                                                                         | `450.0`        |
| `KOL`            | `DECIMAL`     | **Количество в дополнительной единице измерения.** Значение в единицах, указанных в колонке `EDIZM`.                                     | `150`          |
| `TNVED8`         | `VARCHAR`     | **Код ТН ВЭД (8 знаков).** Первые 8 знаков кода `TNVED`, представляющие товарную подкатегорию.                                                | `01012100`     |
| `TNVED4`         | `VARCHAR`     | **Код ТН ВЭД (4 знака).** Первые 4 знака кода `TNVED`, представляющие товарную позицию ТН ВЭД.                                                | `0101`         |
| `TNVED6`         | `VARCHAR`     | **Код ТН ВЭД (6 знаков).** Первые 6 знаков кода `TNVED`, представляющие субпозицию ТН ВЭД.                                                   | `010121`       |
| `TNVED2`         | `VARCHAR`     | **Код ТН ВЭД (2 знака).** Первые 2 знака кода `TNVED`, представляющие группу ТН ВЭД.                                                        | `01`           |
| `SOURCE`         | `VARCHAR`     | **Источник ряда.** Маркер происхождения строки: `national`, `comtrade`, `nowcast`.                                                           | `national`     |
| `TYPE`           | `VARCHAR`     | **Тип ряда.** `fact` для фактических данных, `pred` для nowcast-прогнозов.                                                                    | `fact`         |

> Примечание: в Python-пайплайне `PERIOD` хранится как `datetime64[ns]` (с нормализацией времени `00:00:00`), а при записи в DuckDB приводится к типу `DATE`.

## Формат базы данных `db/unified_trade_data.duckdb`

Файл базы: `db/unified_trade_data.duckdb` (DuckDB).

При запуске merge можно указать другой целевой файл через `--output-db-path`; это удобно для candidate-сборок перед публикацией на дашборд.

Содержимое базы:

- Таблица `unified_trade_data` — основная факт-таблица по схеме выше.
- Таблица `tnved_reference` — справочник ТН ВЭД:
  - `TNVED_CODE` (`VARCHAR`)
  - `TNVED_LEVEL` (`INTEGER`, уровни 2/4/6/8/10)
  - `TNVED_NAME` (`VARCHAR`) — наименование без приклеенной единицы измерения
  - `TNVED_NAME_EN` (`VARCHAR`) — оригинал на английском, из которого сделан машинный перевод;
    заполнен только для `NAME_SOURCE IN ('mt', 'manual')`
  - `TNVED_UNIT` (`VARCHAR`) — дополнительная единица измерения (`ШТ`, `М2`, `КГ P2O5`, …), `NULL` если не задана
  - `NAME_SOURCE` (`VARCHAR`) — откуда наименование: `fts` (справочник ФТС, заморожен 09.02.2022),
    `fns` (классификатор ТНВЭД ФНС, обновляемый), `mt` (машинный перевод из зарубежного источника),
    `manual` (выверено вручную, `metadata/translations/name_overrides.json`)
  - `TRANSLATED` (`BOOLEAN`) — то же, что `NAME_SOURCE = 'mt'`, оставлено для совместимости
- Таблица `tnved_country_chapters` - национальные названия товарных групп:
  - `STRANA`, `TNVED_CODE` - составной первичный ключ (страна ISO2 и двухзначный код)
  - `TNVED_NAME`, `TNVED_NAME_EN` - русское и исходное английское название
  - `SOURCE_URL` - ссылка на источник национального заголовка
  - Заполняется из `metadata/translations/country_chapters.json`. Для Индии группа 98
    имеет национальный заголовок; общий справочник использует нейтральное название.
    Национальная подпись применяется к уровню 2, не наследуется дочерними кодами.
    При объединении стран API сохраняет один агрегат группы с нейтральным названием.
    См. [Национальные названия группы 98](country-chapter-98.md).
- Таблица `country_reference` — справочник стран:
  - `STRANA` (`VARCHAR`, ISO2)
  - `STRANA_NAME` (`VARCHAR`)
- Таблица `hs4_reference` — короткие подписи товарных групп HS4/TNVED4 (из `metadata/hs4_labels.json`):
  - `TNVED4` (`VARCHAR`)
  - `TNVED4_NAME_SHORT` (`VARCHAR`) — краткое название для графиков
  - `TNVED4_NAME_FULL` (`VARCHAR`) — полное русское название
- View `unified_trade_data_enriched` — join `unified_trade_data` со справочниками + вычисляемый `period_rank`.
  Помимо `TNVED_NAME` (самое подробное наименование, каким бы ни было его происхождение) отдаёт:
  - `TNVED_NAME_OFFICIAL` — ближайшее наименование из официального справочника: если на 10 знаках
    лежит машинный перевод, берётся официальный текст на 8, 6, 4 или 2 знаках. Менее подробно,
    зато проверяемо — 99,7 % машинных строк получают официальную подпись на уровне 6 или глубже.
  - `TNVED_NAME_OFFICIAL_LEVEL` (`INTEGER`) — на каком уровне оно нашлось, чтобы было видно,
    насколько огрубили. `NULL`, если официального наименования нет ни на одном уровне.
  - `TNVED_NAME_EN`, `TNVED_UNIT`, `TNVED_NAME_SOURCE` — оригинал, единица измерения и происхождение.
  - `TNVED_TRANSLATED` (`BOOLEAN`) — то же, что `TNVED_NAME_SOURCE = 'mt'`, оставлено для совместимости.
- Таблица `fizob_index` (если есть входные `fizob_*` parquet):
  - `STRANA` (`VARCHAR`)
  - `NAPR` (`VARCHAR`)
  - `PERIOD` (`DATE`)
  - `tn_level` (`INTEGER`)
  - `tn_code` (`VARCHAR`)
  - `fizob` (`DOUBLE`)
  - `fizob_bp` (`DOUBLE`)
- View `fizob_index_v` — надстройка над `fizob_index` с вычисляемой колонкой `idx = fizob / fizob_bp`.
- Таблица `fizob_enriched` — **обогащённый индекс физического объёма**, который читают дашборды
  Superset и API (`/v1/fizob`, OData `fizob`). Это `fizob_index_v`, дополненный названиями и
  кодами-префиксами и перекластеризованный по `STRANA, NAPR, tn_level, tn_code, PERIOD` (для
  быстрых срезов). Индекс считается **только по факту** (`TYPE='fact'`, см. ниже). Столбцы:

  | Колонка | Тип | Описание | Пример |
  |---|---|---|---|
  | `STRANA` | `VARCHAR` | страна-партнёр, ISO2 | `CN` |
  | `COUNTRY_NAME` | `VARCHAR` | название страны (из `country_reference`) | `КИТАЙ` |
  | `NAPR` | `VARCHAR` | направление: `ИМ` (импорт в РФ) / `ЭК` (экспорт из РФ) | `ИМ` |
  | `PERIOD` | `DATE` | отчётный месяц (первое число) | `2024-01-01` |
  | `YEAR` | `INTEGER` | год, производный от `PERIOD` (для группировки/фильтра) | `2024` |
  | `tn_level` | `INTEGER` | **уровень агрегации кода**: `0` — итог по стране, `2` / `4` / `6` — по коду ТН ВЭД в 2 / 4 / 6 знаков | `4` |
  | `tn_code` | `VARCHAR` | код ТН ВЭД на уровне `tn_level`; на уровне `0` (страновой итог) равен `0` | `0101` |
  | `fizob` | `DOUBLE` | физический объём текущего периода (рабочая величина) | `1.12` |
  | `fizob_bp` | `DOUBLE` | физический объём базового периода (знаменатель индекса) | `0.0625` |
  | **`idx`** | `DOUBLE` | **индекс физического объёма** = `fizob / fizob_bp` — главный показатель динамики, очищенный от изменения цен | `0.98` |
  | `TNVED2`, `TNVED4`, `TNVED6` | `VARCHAR` | коды-префиксы (для join/фильтра по группам) | `01` |
  | `TNVED2_NAME`, `TNVED4_NAME` | `VARCHAR` | названия товарной группы/позиции (заполнены на уровнях `2` / `4`) | `ЖИВЫЕ ЖИВОТНЫЕ` |

  > Строки существуют **на каждом уровне отдельно** (`tn_level` 0/2/4/6): при анализе сначала
  > фиксируют один уровень, иначе агрегаты разных уровней смешиваются. Для содержательного
  > показателя берут `idx`; `fizob`/`fizob_bp` — промежуточные величины.

## Ключевые концепции и преобразования

Для вкладки Superset «Физобъемы» и месячных бюллетеней используется общая
витрина `sql/fizob_bulletin.sql`: календарное изменение `fizob` год к году
по всем доступным странам на уровнях 0/2/4/6 и готовый агрегат ALL
по товарным группам 2/4/6. Для ALL уровня 0 витрина восстанавливает
расчетные страновые объемы (`fizob * fizob_bp`), суммирует и нормирует общий
ряд по каждому направлению на первые 12 месяцев. Бюллетени выбирают из нее Китай, Индию и Турцию.
`sql/fizob_trade_context.sql` добавляет размер торговли за текущие и предыдущие
12 месяцев и число месяцев с фактическими записями. Готовый снимок строится локально
скриптом `scripts/build_fizob_bulletin.py`. Подробнее:
[Вкладка «Физобъемы»](superset-fizob.md).

- **Гармонизация:** Основная цель скриптов обработки — взять сырые данные в различных форматах и привести их к этой единой, последовательной структуре. Это позволяет проводить унифицированный анализ по разным странам и периодам времени.
- **Нормализация TNVED:** Товарные коды (`TNVED` и его производные) хранятся в виде строк. Ведущие нули не удаляются, потому что они значимы для групп 01-10. В merge-слое короткие коды дополняются нулями справа до 10 знаков, а производные `TNVED2`, `TNVED4`, `TNVED6`, `TNVED8` формируются как префиксы нормализованного кода.
- **Нормализация периода:** Все индикаторы даты из исходных источников (например, `202301`, `Jan-2023`) нормализуются к первому дню соответствующего месяца (`2023-01-01`).
- **Направление торгового потока:** Колонка `NAPR` является ключевой. Ее значение определяется на основе источника. Например, при обработке данных об *экспорте* из Китая в Россию, для России этот поток является *импортом* (`ИМ`). То есть, для национальных данных необходимо **изменить** направление потока: Export -> `ИМ`, Import -> 'ЭК`. 
- **Стандартизация единиц измерения:** Оригинальные единицы измерения из колонки `EDIZM` сопоставляются со стандартным справочником (`metadata/edizm.csv`) для получения унифицированного кода в колонке `EDIZM_ISO`.
- **Происхождение и тип рядов:** Колонка `SOURCE` фиксирует источник (`national`/`comtrade`/`nowcast`), а `TYPE` разделяет фактические значения (`fact`) и прогноз (`pred`).
- **Nowcast только в «дырах»:** при финальном merge (`merge_processed_data` / `merge_pipeline` + `nowcast_ingest.py`) строки nowcast (`TYPE='pred'`, `SOURCE='nowcast'`) **отбрасываются**, если для той же **торговой ячейки** уже есть хотя бы одна **фактическая** строка (национальные или Comtrade данные, любой `TYPE`, отличный от `pred`). Ключ совпадения: **`PERIOD`** (первая дата месяца), **`STRANA`**, **`TNVED`** после нормализации к 10 символам (как для сопоставления в `nowcast_compare_2026.R`), **`NAPR`**. Единица измерения `EDIZM` в ключ не входит: наличие факта по той же четверке периода/партнер/код/направление блокирует nowcast целиком по этой ячейке. Расчёт прогноза — в `src/nowcast.R`; ingest parquet в unified-схему — в `src/pipelines/nowcast_ingest.py`.
- **Физобъемы считаются только по факту:** `src/fizob_queries.R` читает из `unified_trade_data` только строки `TYPE = 'fact'`. Это защищает индексы физических объемов от смешения фактических рядов и nowcast-прогноза.
- **SQL quality gate:** после финального merge можно выполнить проверки из `src/orchestration/checks.py`: обязательные таблицы/колонки, валидные значения `NAPR`/`SOURCE`/`TYPE`, отсутствие `NULL` в `PERIOD` и отсутствие пересечения `pred` с фактом по торговому ключу.

### Интерпретация динамики fizob в MCP (15.10.2026)

Текущий расчет в `src/fizob_queries.R` использует 12-месячные скользящие средние физических показателей. R нормирует итог на базовый период, а `fizob_index_v` дополнительно делит его на `fizob_bp`. Поэтому абсолютное значение `idx` нельзя автоматически читать как «базовый месяц = 100».
При постоянном положительном знаменателе отношение двух значений одного ряда сохраняет динамику. `compare_trade` использует `(idx_end/idx_start-1)*100` на общих конечных точках фактических данных и показывает каждую страну относительно собственного начала = 100. Это изменение сглаженного индекса между месяцами, не изменение суммы торговли за интервал.
На товарных уровнях используются меняющиеся стоимостные веса. На уровне 0 агрегация товаров с разными физическими единицами является осознанной особенностью методологии fizob и предназначена для анализа динамики разнородной товарной корзины. Наличие разных единиц само по себе не является методологическим недостатком индекса. Это следует отличать от простого сложения сырых значений KOL без учета единиц. Формулы базы данным изменением не исправляются. Подробнее: `mcp-server/README.md`, раздел «Fizob в compare_trade».

## Физические показатели и оценки источника (15 октября 2026)

Схема Фишера `fisher_annual_v2` опубликована 24 октября 2026 после локального
пересчета сентябрьских данных. В ней `fizob` уже нормирован к базе 1,
`bp` хранит дату базового года, а совместимый `fizob_bp` равен 1.
Загрузчик сохраняет дату базы, индекс цен, статус, покрытие окон, доступную
стоимость и долю вменённых цен. Пропуски не заполняются нулями; г/г между
разными базами не рассчитывается. Смешивать старые и новые файлы в одной
таблице запрещено. Подробности и локальные проверки:
[Аудит и исправления нового fizob](fizob-fisher-audit-2026-10-24.md).
Текущий выпуск, проверки и откат:
[Сентябрьская сборка](september-release-2026-10-24.md).
Неполные общие индексы остаются NULL. API передает `base_period`,
`methodology_version`, `status`, `coverage`; чат, MCP и экспортное сравнение
не рассчитывают отношение индексов между разными базами цепочки.

### Реестр публикаций и подтвержденные нули

`metadata/publication_registry.json` содержит проверенные публикации и ссылки
на манифесты Comtrade. `core.publication_registry` различает полноту публикации,
успешность загрузки и семантику отсутствующих строк. Старые записи Comtrade без
статуса загрузки имеют статус `unknown`, даже если файл существует.

Сборка Fisher вызывает `scripts/prepare_fisher_publication_zeros.py`
и сохраняет отдельный `confirmed_absence.parquet` в новой директории результатов.
Для заполнения отсутствующей стоимости нулем одновременно необходимы:
`publication_status=confirmed_complete`, `download_status=complete`,
`absence_semantics=zero_for_applicable_codes`, подтверждения семантики и
применимости кодов, совпадающий SHA256 исходного файла, явный список действующих
10-значных кодов. Исключенные префиксы, существующие наблюдения, включая nowcast,
не заменяются. Масса и количество не выводятся из отсутствия стоимостной строки.
Синтетическая строка имеет `OBSERVATION_STATUS=confirmed_absence` и `RELEASE_ID`;
ее происхождение сохраняется в отдельном файле, рабочая база не изменяется.

В первоначальном реестре четыре подтвержденные публикации Китая, но семантика
отсутствующих кодов остается `unknown`. Поэтому текущие данные не получают
автоматических нулей. Исторический набор кодов пока не заменен таблицей их
применимости; неполные агрегаты остаются неполными.

Comtrade при достижении предела ответа делит запрос по странам и направлениям.
Если отдельное направление все еще обрезано, публикация страны не заменяется,
получает `download_status=truncated` и повторно запрашивается при проверке
обновлений. Успешный ответ другого направления не применяется отдельно.
Последний успешный checksum сохраняется. `complete` означает завершенную
загрузку, а не доказанное отсутствие торговли по отсутствующим кодам.

Предварительная локальная проверка 24.10.2026: 38 880 строк группы 27 и общего агрегата совпали
с предыдущим строгим расчетом. Тест с подтвержденным отсутствием закрывает
пропуск обоих агрегатов без изменения доступной стоимости. На этом этапе прод
не обновлялся; результат последующей публикации приведен в отчете о сентябрьской сборке.
Для R-сборки путь к Python можно задать через `FIZOB_PYTHON`.

Проверка правил источников: [Китай и Comtrade](source-absence-rules-2026-10-24.md).
Реестр содержит официальные основания в `source_rules` и выявленные расхождения
группы 27 с детализацией в `detail_coverage_findings`. Для разрешения новых нулей
по этим источникам требуется отдельное `absence_evidence` конкретного выпуска.
Выявленное расхождение блокирует вывод нулей в соответствующем срезе.

Оригиналы Китая теперь архивируются до обработки, вместе с параметрами и
примечаниями; проверка не пропускает поврежденные CSV-строки. Порядок получения
новых файлов и результаты проверки девяти кодов группы 27:
[Оригинальные выгрузки Китая](china-original-exports-2026-10-24.md).

- `SOURCE_UNIT` сохраняет обозначение единицы до общей нормализации.
- `SOURCE_QTY_ESTIMATED` и `SOURCE_NETTO_ESTIMATED` сохраняют исходные признаки оценки Comtrade.
- `KOL_ESTIMATED` и `NETTO_ESTIMATED` относятся к выбранным значениям количества и массы: `true` означает оценку источника, `false` означает отсутствие такой пометки у источника, `null` означает неизвестный статус. Для альтернативного количества Comtrade отдельного флага в текущих исходных данных нет; статус не подменяется на `false`.
- `TYPE=fact` означает отсутствие nowcast проекта, но допускает оценки физических показателей самим источником. Они передаются в `quality_flags` и описании Excel-выгрузки.
- Неизвестная масса остается `NULL`, а не нулем. Восстановление допускается из положительного количества в явно указанных килограммах, граммах или тоннах с переносом признака оценки и предупреждением.
- Индийские SQM, PRS, MTR, CBM нормализуются в квадратные метры, пары, метры и кубические метры. Неоднозначные обозначения сохраняются без выдуманного стандартного кода.
- Дюжины, комплекты/упаковки, грузоподъемность и масса без жидкости не приравниваются к штукам или массе нетто поставки. Значение и единица выбираются только связанной парой.
- При агрегировании предупреждения сохраняются. Если масса хотя бы одной строки неизвестна, сумма не выдается как полный итог. Разные единицы количества нельзя суммировать напрямую; это не ограничение методологии индекса fizob, который допускает агрегирование разных единиц.
