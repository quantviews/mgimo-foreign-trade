# Развертывание на сервере МГИМО 146

Дата первичного переноса: 8 ноября 2026 года. Сервер `172.17.0.146`,
hostname `prod-146`, SSH-пользователь `stp`. Публичный домен `nts.mgimo.ru`
разрешается в `194.190.140.146`. Старый VPS Beget не используется этим стеком.

## Ограничения и текущее состояние

- Все загрузки исходных данных, nowcast, fizob и сборки DuckDB выполняются на ПК.
  На сервер передаются проверенные готовые файлы. Docker-образы разрешено собирать на сервере.
- Бекап перед этим переносом пропущен по явному указанию владельца проекта.
  Автоматическое резервирование готового сервера пока не настроено.
- Старая `tradeapi` отсутствовала. Создана новая база, история чата, старые
  API-ключи и регистрации с Beget не восстановлены. Пользовательские ключи
  выпускаются через кабинет Superset после входа с существующей ролью API.
- Демо-сервис запущен и открыт. DeepSeek и SMTP настроены 8 ноября.
  Временные ответы 503 для `/demo/register` и `/demo/chat` сняты после проверок.
- Внутренняя делегация Excel для демо-сервиса включена с отдельного разрешения
  владельца. Файлы должны создаваться с владельцем из проверенной сессии.
- Wildcard-сертификат МГИМО обновлен 9 ноября 2026 года. Срок действия заканчивается
  **20 мая 2027 в 15:22:31 МСК**. Цепочка GlobalSign и соответствие ключа проверены.

## SSH

На Windows установлен публичный ключ текущего пользователя для `stp`:

```powershell
ssh -o BatchMode=yes stp@172.17.0.146 "hostname; whoami"
```

Приватный SSH-ключ не передается на сервер. Пароли и содержимое `.env` не выводить
в логи. `sudo` требует пароль; пользователь имеет доступ к Docker.

## Первичное развертывание

1. Снять инвентаризацию контейнеров, томов и баз, проверить свободное место.
2. Проверить локальную DuckDB и Parquet, записать SHA-256 и размер в манифест.
3. Передать исходники `api`, `demo`, `mcp-server`, `shared`, `superset_cabinet`,
   `deploy/mgimo146` и `.dockerignore` в `/home/stp/mgimo-trade`.
   Не включать исходные данные, `.env`, TLS-ключи или содержимое `.git` в архив исходников.
4. Передать готовые данные и TLS отдельно в приватный staging-каталог (`0700`).
5. Только для пустой служебной базы выполнить `bootstrap.py` из этого каталога.
   Он создает роль `tradeapp`, базу `tradeapi`, применяет миграции 001-012,
   сохраняет их контрольные суммы и генерирует внутренний ключ демо-сервиса.
   Конфигурации `api.env`, `demo.env`, `cabinet.env` имеют права `0600`.
   Повторный bootstrap существующей базы запрещен самим скриптом.
6. Собрать образы. Docker Compose 5.6 использует Bake и требует явного разрешения host-сети:

```bash
cd /home/stp/mgimo-trade/deploy/mgimo146
docker buildx bake -f compose.yml \
  --allow=network.host --allow=fs.read=/home/stp/mgimo-trade --load
```

7. Установить данные скриптом `install_artifacts.py`. Он копирует файлы через
   `.new`, проверяет SHA-256 до и после копирования и выполняет `os.replace`.
   Пример с уже установленным образом Superset, без сетевого доступа:

```bash
docker run --rm --network none --user 0 --entrypoint python \
  -v /home/stp/mgimo-stage-20261108:/stage:ro \
  -v /srv/duckdb:/target/duckdb \
  -v /srv/parquet:/target/parquet \
  -v /opt/mgimo-landing/certs:/target/certs \
  mgimo-superset:6.1.0 /stage/install_artifacts.py
```

Этот helper имеет запись только в указанные каталоги. Он не выполняет расчеты
данных. В staging требуются `data-manifest.json`, файлы базы и витрины,
`mgimo-fullchain.pem`, `key.txt`, сам скрипт. Публикацию базы и витрины считать
единым выпуском: остановить потребителей при последующих обновлениях, чтобы
запросы не читали смесь разных выпусков между двумя заменами файлов.

8. `configure_host.py` подключает кабинет Superset к новой `tradeapi` и копирует
   актуальный модуль кабинета, сохраняя остальные параметры Compose. Пароли не печатаются.
9. Запустить новые приложения и пересоздать Superset/worker/beat для нового окружения:

```bash
docker compose -f compose.yml up -d --no-build
cd /opt/mgimo-superset
docker compose up -d --no-build --force-recreate superset worker beat
```

10. Внутри контейнера Superset выполнить `finish_superset.py`, затем
    `scripts/configure_superset_fizob.py` из репозитория. Второй скрипт меняет
    только датасеты и графики вкладки, используя готовый Parquet.
11. Установить nginx-конфигурацию из `deploy/mgimo146/nginx.conf`, проверить
    `nginx -t`, затем выполнить reload. При незаполненных секретах чата сохранить
    временные exact-match ответы 503 для `/demo/register` и `/demo/chat`.
12. Опубликовать готовые HTML/CSS/JS/PDF/XLSX, собранные локально. Не копировать
    старые сборки поверх новых страниц. Не возвращать снятую с публикации KVE-презентацию.

## Подключение DeepSeek и почты

Локальный шаблон `demo/.env` создан из `demo/.env.example` и исключен из Git.
Владелец заполняет ключ `MGIMO_DEMO_DEEPSEEK_API_KEY` и настройки SMTP.
На сервер переносить только параметры провайдера и почты. Не перезаписывать
сгенерированные DSN, service key и session secret значениями из шаблона.
Не менять модель без отдельного решения владельца.

После настройки проверить доступность провайдера и SMTP. Тестовое письмо
отправлять только с разрешения пользователя. Пересоздать демо-контейнер,
проверить реальный диалог и Excel с пользовательской сессией. Затем убрать
временные ответы 503 из nginx и выполнить `nginx -t` / reload.
`/demo/health` подтверждает работу процесса, но не готовность модели и SMTP.

## Повторное обновление

1. Локально собрать и проверить данные и сайт. Подготовить манифест с версией,
   SHA-256, числом строк, периодом и результатами проверок.
2. Согласовать короткое окно обновления. После настройки бекапов проверять
   успешную копию до изменений; отказ от бекапа 8 ноября не является постоянным правилом.
3. Загрузить выпуск в отдельный staging-каталог. Собрать образы с уникальным
   `RELEASE_TAG`, например `20261108-<git-sha>`, и сохранить используемые image ID.
4. Новые SQL-миграции применять по порядку с проверкой журнала
   `public.deployment_migrations`. Не запускать bootstrap заново и не применять
   старые миграции вслепую. Проверять совместимость схемы при откате приложения.
5. Остановить API/demo/MCP и Superset/worker/beat на время замены данных.
   PostgreSQL и Redis оставлять работающими. Проверить файлы, заменить базу и витрину.
6. Запустить сервисы, очистить только кеш результатов графиков, выполнить приемку.
   При штатном обновлении предыдущий выпуск и дамп должны позволять откат.

## Замена TLS

9 ноября установлена новая пара для `*.mgimo.ru` и `mgimo.ru`. Публичный SHA-256
сертификата: `f89598df93e939ace0aba966183d77b66c4e856bf47ba804c0e49bc85fb808f8`.
Предыдущая пара сохранена в `/opt/mgimo-landing/certs/.previous-20261109`
(каталог `0700`, ключ `0600`). Выполнены `openssl verify -verify_hostname`,
проверка совпадения публичных ключей, `nginx -t` и reload без остановки сервисов.
Новый сертификат проверен через публичный HTTPS с обычной проверкой доверия;
лендинг, демо, вход Superset, favicon, Swagger и OAuth discovery отвечают 200.
Сами сертификаты, ключи и архивы не хранятся в Git и не входят в Docker-контекст.

Получить новый сертификат, промежуточную цепочку и соответствующий ключ от ИТ.
Проверить SAN `*.mgimo.ru` или `nts.mgimo.ru`, срок действия и совпадение публичного
ключа сертификата с приватным ключом. В `mgimo-fullchain.pem` поместить сначала
сертификат сайта, затем промежуточные сертификаты. Корневой сертификат обычно
не включается в отправляемую сервером цепочку.

Ключ хранить с правами `0600`. После замены файлов:

```bash
docker exec mgimo-landing-landing-1 nginx -t
docker exec mgimo-landing-landing-1 nginx -s reload
curl --resolve nts.mgimo.ru:443:127.0.0.1 https://nts.mgimo.ru/api/health
```

Не использовать отключение проверки TLS как критерий успешного ввода.
