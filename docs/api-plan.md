## Привязка к пунктам договора (трассируемость)

| Пункт 2.3 | Реализация |
|---|---|
| разработка системы программного доступа к данным через API | сервис FastAPI поверх DuckDB (read-only), REST-эндпоинты по ресурсам `/trade`, `/fizob`, `/reference` |
| авторизация пользователей | токены (API-ключ на пользователя), хранилище пользователей/токенов, скоупы/роли, HTTPS |
| мониторинг использования системы отдельными пользователями | аудит-лог каждого запроса (пользователь, эндпоинт, параметры, строки, латентность, статус) + дашборд использования в Superset |
| доступ к данным из Microsoft Excel | эндпоинты, потребляемые Power Query («Из интернета»/OData), Basic-auth для совместимости с Excel |

## Архитектура (общая)

```
Excel / скрипты / BI
        │  HTTPS + токен
        ▼
   nginx (TLS, rate-limit)
        │
        ▼
   FastAPI-сервис  ──►  DuckDB (read-only, connection pool)  [unified_trade_data.duckdb]
        │
        ├─►  Хранилище пользователей/токенов (SQLite/Postgres/DuckDB)
        └─►  Аудит-лог запросов (таблица) ──►  Superset «Использование API»
```

Ключевой принцип: **DuckDB встраиваемая, без сети/авторизации** — весь доступ, токены и
мониторинг живут в сервисе перед файлом. DuckDB открыт **read-only** (много одновременных
читателей в одном процессе). Пересборка БД — офлайн, со свопом файла и переоткрытием
коннектов.

## Компоненты

### 1. Сервис (FastAPI)
- Python-стек (совпадает с проектом), `uvicorn`/`gunicorn` за `nginx`.
- Пул read-only коннектов к DuckDB; параметризованные запросы (защита от инъекций).
- Свои модули-роутеры: `trade`, `fizob`, `reference`, `admin` (управление токенами), `usage`.
- Форматы ответа: JSON (по умолчанию), CSV (`?format=csv`) — CSV удобен для Excel/выгрузок.
- Лимиты: max строк на ответ, пагинация (`limit`/`offset` или cursor), таймаут запроса.

### 2. Авторизация
- **Модель:** персональный статический API-ключ (bearer-токен) на пользователя.
- **Личный кабинет — страница внутри Superset** (кастомный view Flask-AppBuilder): пользователь
  логинится в Superset (единая учётка/SSO), на странице «Мой API-ключ» видит/перевыпускает токен.
  Так «единая среда со Superset» достигается по-настоящему — одна авторизация, один вход.
- **Саморегистрация — на механизме Superset** (Flask-AppBuilder `AUTH_USER_REGISTRATION=True`
  с подтверждением по email/SMTP): пользователь сам регистрируется, попадает в кабинет, выпускает
  токен, авто-план «pilot». Отдельный портал не нужен.
  - ⚠️ **Локдаун роли по умолчанию:** самозарегистрированным давать **минимальную роль**
    (доступ только к кабинет-странице), НЕ к внутренним дашбордам/SQL Lab Superset. Иначе
    публичная регистрация откроет внутреннюю аналитику. Опционально — CAPTCHA/rate-limit на
    регистрацию против ботов.
- Хранилище: таблица `users` (id, name, org, scopes, active) + `tokens` (hash токена, user_id,
  created, expires, last_used) в **Postgres** (см. §3). Токены хранить **хешированными**.
- **Совместимость с Excel:** поддержать HTTP **Basic-auth**, где токен идёт как пароль —
  Power Query это принимает нативно (в отличие от кастомных заголовков). Плюс `Authorization:
  Bearer` для программных клиентов.
- **Скоупы/роли** (опционально, но заложить): напр. `trade:read`, `fizob:read`, `all` —
  чтобы можно было выдавать доступ по доменам.
- HTTPS обязателен (токены в трафике). Rate-limit на токен (в nginx или в приложении).

### 3. Мониторинг использования (требование договора)
- **Аудит-лог**: на каждый запрос писать строку — `ts, user_id, endpoint, params(json),
  rows_returned, bytes, latency_ms, status, ip`. Append-only.
- **Хранилище токенов и аудит-лога — Postgres** (тот же инстанс, что у Superset, отдельная
  схема). Обоснование: аудит-лог пишется на каждый запрос **конкурентно**, а SQLite/DuckDB —
  однописательные и для этого не годятся. Postgres у Superset в проде обычно уже есть →
  переиспользуем инфраструктуру и получаем единство с кабинетом.
- **Дашборд «Использование API» в Superset** поверх аудит-лога: запросы по пользователям,
  топ-эндпоинты, объёмы, ошибки, динамика. Закрывает формулировку «мониторинг использования
  отдельными пользователями» наглядно и переиспользует уже имеющийся Superset.
- Метрики сервиса (Prometheus-эндпоинт) — опционально, для тех-мониторинга.

### 4. Доступ из Excel
Проблема русской локали: Excel использует `;` как разделитель списка (`,` занята под
десятичный знак), а UTF-8 без BOM читается кракозябрами — это боль **открытия CSV двойным
кликом**. Решение — не CSV, а типизированный формат через Power Query.

- **v1 (рекомендуется): JSON через Power Query.** «Получить данные → Из интернета», Basic-auth
  (токен = пароль). JSON типизирован, всегда UTF-8, **без разделителей вообще** — проблема
  русских `;`/кодировок исчезает. Power Query разворачивает JSON в таблицу нативно, обновление
  кнопкой. Проще полноценного OData.
- **v2 (нативнее): OData-фид** (минимальный OData v4: entity sets + `$filter`/`$select`/`$top`) —
  Excel «Из веб-канала OData»: типизированные данные + серверная фильтрация (Excel тянет только
  нужное) + инкрементальное обновление. Дороже в реализации.
- **CSV — как опция** для тех, кто открывает напрямую: отдавать с **UTF-8 BOM** и разделителем
  `;` (или строкой-директивой `sep=;`).
- Приложить инструкцию для аналитиков (скриншоты Power Query + где взять токен в кабинете).
- Опция на будущее (если попросят «живой SQL» из Excel) — Postgres-wire фронт поверх DuckDB
  и стандартный Postgres-ODBC. В v1 избыточно.

## Поверхность API (черновик)

- `GET /v1/trade` — фильтры: `strana`, `napr`, `type`, `source`, `tnved2/4/6`, `period_from`,
  `period_to`; агрегация: `group_by`, метрики `stoim/netto/kol`; `format`, `limit`, `offset`.
- `GET /v1/fizob` — `strana`, `napr`, `tn_level`, `tn_code`, `period_from/to`; отдаёт `fizob`,
  `fizob_bp`, `idx`.
- `GET /v1/reference/countries`, `GET /v1/reference/tnved?level=` — справочники (для выпадашек).
- `GET /v1/meta` — доступные измерения/диапазон дат/версия данных.
- `POST /admin/tokens` (роль админа) — выпуск/отзыв токенов.
- `GET /usage` — своя статистика использования (пользователю — своя, админу — всех).
- Всё read-only; параметры валидируются (Pydantic), запросы — параметризованные к DuckDB.

## Безопасность
- HTTPS (TLS в nginx). Токены — только по HTTPS, хранить хешированными.
- DuckDB-коннект read-only; **никакого сырого SQL от пользователя** в v1 (только
  параметризованные эндпоинты). Если позже добавлять SQL-эндпоинт — строгий парсер/allowlist,
  запрет `ATTACH`/`COPY`/`PRAGMA`/записи.
- Лимиты строк/размера ответа, таймауты, rate-limit — против тяжёлых/абьюзивных запросов.
- Валидация всех фильтров; коды ТНВЭД/страны — по справочнику.

## Развёртывание / эксплуатация
- On-prem, рядом с Superset (тот же VPS или соседний). Docker/systemd.
- БД — тот же артефакт, что и для Superset; при пересборке пайплайна — атомарный своп файла
  и переоткрытие read-only коннектов (сигнал/health-reload, чтобы не рвать активные запросы).
- Один процесс FastAPI обслуживает много читателей; масштабирование — воркерами `gunicorn`.

## Коммерциализация (freemium — заложить сейчас, включить позже)

Сервис видится будущим коммерческим: бесплатно на пилоте → бесплатный тариф с лимитами по
запросам → больше за деньги. Чтобы это стало «включением», а не переписыванием, закладываем
каркас сразу.

Принципы:
1. **Метрить с первого дня.** Аудит-лог (и так по договору) = источник истины для биллинга;
   каждый запрос пишем с «единицами стоимости» (`cost_units`). Счёт = агрегация лога.
2. **Тарифы как данные.** Таблица `plans` (`rate_limit`, `monthly_quota`, `scopes`, `max_rows`,
   `history_years`, …) + `user.plan_id`. В пилоте всем — план «pilot» (щедрые/безлимитные
   лимиты). Коммерциализация = добавить платные планы + включить enforcement, без переархитектуры.
3. **Разделить метринг и биллинг.** API метрит и проверяет квоты; платёжный модуль — отдельно,
   позже, читает usage+plan → счета. Провайдера оплаты сейчас не вшиваем.
4. **Enforcement — middleware:** rate-limit (против абуза) + месячная квота из быстрой
   rollup-таблицы `usage_by_user_month`. В пилоте — высокие/выключенные лимиты.
5. **Кабинет в Superset** = коммерческая витрина: план, «использовано X из Y за месяц», позже —
   апгрейд/оплата.

Единица тарификации: **запрос/месяц + rate-limit** (просто, предсказуемо) + cap строк на запрос
как guardrail. Построковый биллинг — позже, если понадобится точнее отражать ценность.

Что делаем **сейчас** (дёшево, future-proof): `plans` + `user.plan` + аудит с `cost_units` +
middleware квот (щедрое в пилоте) + rollup `usage_by_user_month` для кабинета.
Что **откладываем**: интеграция оплаты (для РФ — ЮKassa/CloudPayments, не Stripe),
самообслуживаемый апгрейд плана, overage-биллинг.
**Нетехническая предпосылка платного доступа:** ToS + лицензия на данные.

## Фазы

- **Фаза 1 (MVP):** FastAPI + read-only DuckDB + API-ключи (Basic+Bearer) + 3–4 curated
  эндпоинта по торговле (JSON, потребление через Power Query) + аудит-лог с `cost_units` +
  таблицы `plans`/`user.plan` (всем план «pilot»). Кабинет-страница в Superset (показать токен).
  Инструкция Power Query для аналитиков.
- **Фаза 2:** enforcement квот/rate-limit (middleware) + rollup `usage_by_user_month`; дашборд
  «Использование API» в Superset; в кабинете — «использовано X из Y»; эндпоинты fizob;
  выдача/отзыв токенов в кабинете.
- **Фаза 3 (коммерция):** платные тарифы + декуплённый биллинг (ЮKassa/CloudPayments);
  OData-фид для Excel/BI; скоупы/роли; тех-мониторинг (Prometheus). При спросе — Postgres-wire
  для «живого SQL» из Excel.

## Решения (2026-07-30)

1. **Токены:** статические персональные API-ключи. Личный кабинет — **страница внутри Superset**
   (единая среда).
2. **Хранилище токенов/аудита:** **Postgres** (используется, тот же инстанс, что у Superset).
3. **Excel v1:** **JSON через Power Query** (снимает проблему `;`/кодировок); OData — в v2;
   CSV — опция с UTF-8 BOM + `;`.
4. **Хостинг:** тот же VPS, что Superset (общий Postgres). **TLS пока нет** (домен не готов) —
   пилот по HTTP на :8090 за фаерволом/SSH-туннелем; nginx-конфиг TLS-ready под будущий домен.
5. **Коммерциализация:** freemium — каркас тарифов/квот/метринга закладываем с Фазы 1
   (см. раздел «Коммерциализация»), платные планы и биллинг включаем в Фазе 3.
6. **Выдача токенов:** **без саморегистрации** — пользователей заводит админ в Superset и
   назначает роль-допуск (напр. `API`); пользователь с этой ролью выпускает свой токен на
   странице-кабинете внутри Superset (`superset_cabinet/`). Единица тарификации — **позже**.
